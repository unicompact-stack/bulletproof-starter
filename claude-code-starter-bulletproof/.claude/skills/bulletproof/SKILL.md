## Главный принцип

**Код решает задачу, а не пишется ради кода.**

Перед КАЖДЫМ изменением спроси: «Это реально решает нашу задачу? Это самое эффективное решение?»
Если ответ неясен — стоп, исследуй альтернативы, выбери лучшую.

---

## Выбор режима

Не каждой задаче нужен полный конвейер.

| Размер | Примеры | Режим | Этапы |
|--------|---------|-------|-------|
| **S** | Баг-фикс, мелкая правка, 1-2 файла | Лёгкий | 1 → 4 → 5 → 6 → 7 → Гейты (без спеки и плана) |
| **M** | Новая фича, рефакторинг модуля, 3-10 файлов | Стандартный | Этапы 1-10 |
| **L** | Смена архитектуры, новый сервис, 10+ файлов | Полный | Этапы 1-12 (все) |

**Как связаны этапы:** этапы 5-6-7 (Самопроверка, Верификация, Анализ влияния) идут **внутри каждой фазы** реализации как внутренний цикл. Этапы 8-12 — **один раз после всех фаз** как внешний цикл.

**Определи размер до старта** и скажи пользователю: «Задача размера M, иду по этапам 1-10».

## Контекст бизнеса (обязательно для этого шаблона)

Перед этапом 1 прочитай `.business/INDEX.md` и только те файлы, которые относятся к задаче
(правило: читай нужное, не загружай всё сразу).

**Зачем:** Bulletproof проверяет, что код решает задачу. Но «задача» задана бизнесом —
если не понять контекст, можно безупречно реализовать не то, что нужно.
Спека (этап 2) должна быть согласована с `.business/products/`, `.business/audience/` и `.business/goals/`.

## Управление контекстом (работает всегда)

### Правило 40%
Качество кода падает, когда контекст заполнен больше чем на 40% («зона тупости»). Правила:
- Держись в пределах 40-60% окна контекста
- Ручной `/compact` на 50% — не жди автоматического
- Если перегружен: сохрани прогресс → `/clear` → начни заново

### Свежий контекст между этапами
Каждый крупный этап = чистое окно контекста:
1. Сохрани артефакт этапа (исследование / спека / план / handoff)
2. `/clear`
3. Начни новый этап, указав агенту путь к артефакту

### Протокол handoff
Перед `/clear` всегда создавай `progress/<задача>-handoff.md`.
Формат — `templates/handoff.md`.

### Дозированная загрузка
Не вываливай весь кодовую базу в контекст:
- Исследование: субагенты → компактная сводка
- Планирование: сводка + ключевые интерфейсы
- Реализация: только файлы текущей фазы
- В CLAUDE.md: `"Подробнее — см. путь/к/файлу.md"` (не `@file`)

## Этап 1. Глубокое исследование

**Режим: только чтение. Без кода. Без изменений.**

- Запусти параллельных Explore-агентов (по одному на направление: структура, паттерны, зависимости, тесты)
- **WebSearch: кто уже решил эту задачу? Как именно? Какое решение считается лучшим?** Не изобретай — сначала найди готовый лучший подход.
- **Проанализируй находки и сделай вывод: какое решение ЛУЧШЕЕ и почему.** Артефакт должен заканчиваться конкретной рекомендацией, а не списком вариантов.
- Сохрани в `research/YYYY-MM-DD-<задача>.md`
  (формат — `templates/research.md`)

**→ `/clear`**

---

## Этап 2. Спека (PRD)

**Режим: чтение + запись только в `specs/`. Без кода.**

**Спека = ЧТО и ЗАЧЕМ. Не как. Спека = контракт.**

- Прочитай артефакт исследования из `research/`
- Создай `specs/YYYY-MM-DD-<название>.md`
  (формат — `templates/spec.md`)
- Ключевые разделы: Проблема, Цель, Область, Критерии приёмки, Ограничения, Не-цели
- **Сверь цель спеки с `.business/`** — если фича противоречит целям из `.business/goals/` или не закрывает боль из `.business/audience/avatar.md`, скажи об этом пользователю до начала работы.

**Пропускается для задач размера S.**
**→ `/clear`**

---

## Этап 3. Планирование + вопросы

**Режим: чтение + запись только в `plans/`. Кода ещё нет.**

- Прочитай **и** спеку (`specs/`), **и** исследование (`research/`)
- Запусти Plan-агентов для проверки подхода
- Ищи дыры: что не продумано? Какие краевые случаи? Что может сломаться?
- **Будь проактивным: предвосхити ВСЕ возможные проблемы ДО написания кода.** Думай на несколько шагов вперёд. Что пойдёт не так через неделю? Через месяц? Под нагрузкой? При неожиданном поведении пользователя? Решай проблемы до того как они возникнут.
- **WebSearch: как другие решали эту же задачу? Какие библиотеки/паттерны есть? Какая практика считается проверенной?** Выбирай самое эффективное решение, а не первое пришедшее в голову.
- После проверки Plan-агентами — **перепиши план в улучшенную версию**, включив все находки, краевые случаи и результаты исследования. Не латай — перепиши лучше.

### Challenge Loop (обязателен перед финализацией плана)

```
Перед финализацией плана ответь на 3 вопроса:

1. ЭТО РЕШАЕТ ЗАДАЧУ?
   Сверь каждый пункт плана с критериями приёмки из спеки.
   Если какой-то критерий не покрыт — план неполный.

2. ЭТО САМОЕ ЭФФЕКТИВНОЕ РЕШЕНИЕ?
   Найди: кто уже решал эту задачу? Какой подход выбрали?
   Назови 2-3 альтернативных подхода (включая найденные в исследовании).
   Для каждого: плюсы, минусы, трудозатраты.
   Обоснуй, почему выбранный подход лучше всех альтернатив.

3. ЕСТЬ ЛИ «КОД РАДИ КОДА»?
   Каждое изменение должно служить критериям приёмки.
   Если изменение не связано с решением задачи — удали его.
   Попутный рефакторинг = отдельная задача, не часть этой.
```

### Цикл аннотаций
1. Клод пишет черновик плана
2. `Ctrl+G` — план открывается в редакторе
3. Пользователь добавляет аннотации `> NOTE:`
4. Клод: «Разбери все замечания, пока не реализуй»
5. Повторяй, пока замечаний не останется

### Вопросы пользователю
- Только когда есть реальный выбор
- Используй AskUserQuestion с вариантами
- К каждому вопросу: **рекомендуй вариант, который считаешь лучшим, и объясни почему**
- Не спрашивай очевидного

### Дополнительная критика (для задач M и L)
Прогони план через 3 параллельных субагента — промпт в
`prompts/methodology/plan-critique.md` (техника / бизнес-контекст / UX).
Это дополняет Challenge Loop, не заменяет его: Challenge Loop = 3 вопроса самому себе,
критика субагентами = взгляд извне.

### Финальный план
Создай `plans/YYYY-MM-DD-<название>.md`
(полный шаблон — `templates/plan.md`; лёгкая версия для задач S — `plans/TEMPLATE.md`)

**→ `/clear`**

## Этап 4. Реализация по фазам

**Каждая фаза = отдельная сессия, свежий контекст, своя ветка.**

Фазы можно вести **параллельно** в отдельных сессиях/терминалах Claude Code, если они не зависят друг от друга. Проверь зависимости в плане перед распараллеливанием.

**Стоп-фраза перед началом кода:** реализация начинается только после финализации плана и разбора всех аннотаций. Триггер: `"Реализуй фазу N по плану."`

Порядок внутри фазы:
1. Создай/переключись на ветку: `feature/<задача>`
2. Статус → `in_progress`
3. **TDD**: тесты СНАЧАЛА (красные)
4. **Реализация**: код, чтобы тесты прошли (зелёные)
5. **Рефакторинг** (если нужен)
6. **Самопроверка** (этап 5)
7. **Верификация** (этап 6)
8. **Анализ влияния** (этап 7)
9. **Гейты** (см. раздел «Гейты»)
10. **Коммит** (чекпоинт для отката)
11. Статус → `completed`, запись в Changelog плана
12. **Handoff** → `/clear`

## Этап 5. Самопроверка (после каждой фазы)

**Обязательна ПЕРЕД отметкой `completed`:**

```
Проверь реализацию фазы:

1. СООТВЕТСТВИЕ СПЕКЕ
   Открой спеку. Пройди по каждому критерию приёмки.
   Для каждого: реализовано? Где именно в коде?
   Если что-то не покрыто — доделай.

2. ПРОВЕРЬ РЕШЕНИЕ
   Посмотри на написанный код свежим взглядом.
   Он реально решает проблему из спеки?
   Есть ли способ проще / эффективнее?
   Есть ли «код ради кода» — изменения, не связанные с задачей?
```

## Этап 6. Верификация — глубокая охота за багами

**Не только линтер. Вдумчивая проверка с фильтрацией ложных срабатываний.**

### Шаг 1: Найди ошибки
```
Проверь ВЕСЬ код этой фазы на:
- Логические ошибки (неверные условия, off-by-one, состояние гонки)
- Работа с данными (null/undefined, несовпадение типов)
- Безопасность (инъекции, обход авторизации, раскрытые секреты)
- Производительность (N+1 запросы, утечки памяти, лишние ре-рендеры)
```

### Шаг 2: Докажи, что баги реальны
```
Для КАЖДОГО найденного бага:
1. Это РЕАЛЬНЫЙ баг или ложное срабатывание?
2. Можешь доказать, что баг воспроизводится?
3. Если доказать не можешь — это НЕ баг. Не трогай.

ПРАВИЛО: не чини код «ради красоты» и «на всякий случай».
Чини ТОЛЬКО доказанные баги, которые реально влияют на работу.
Каждое «исправление» без доказательства = риск внести новый баг.
```

### Шаг 3: Проверка логики и эффективности
```
Финальная проверка чистоты кода:
- Логика: правилен ли поток данных от входа к выходу?
- Эффективность: есть ли лишние операции?
- Читаемость: понятен ли код без комментариев?
НО: не рефактори «ради красоты». Только если влияет на корректность.
```

## Этап 7. Анализ влияния — «Мы ничего не сломали?»

**Самый недооценённый этап. 75% ИИ-агентов ломают работающий код.**

```
ОБЯЗАТЕЛЬНАЯ ПРОВЕРКА ПЕРЕД MERGE:

1. РЕГРЕССИИ
   Какие модули/функции зависят от изменённых файлов?
   Запусти ВСЕ тесты проекта (не только текущей фазы).
   Если что-то сломалось — это приоритет №1.

2. ПОБОЧНЫЕ ЭФФЕКТЫ
   Изменились ли контракты/интерфейсы (API, props, типы)?
   Если да — кто их использует? Все ли потребители обновлены?

3. ЗАГЛЯНИ ВПЕРЁД
   Какие проблемы эти изменения вызовут через неделю/месяц?
   Какие краевые случаи мы не протестировали?
   Что будет: с нулевыми данными? С огромными? При параллельных запросах?
   Что если пользователь сделает что-то неожиданное?

4. СОВМЕСТИМОСТЬ
   Обратная совместимость сохранена?
   Нужны ли миграции данных?
   Нужны ли фиче-флаги для постепенного раската?
```

## Этап 9. Код-ревью (свежий контекст)

**Новая сессия. Без предвзятости реализатора.**

- Запусти агента `@code-reviewer` (см. `agents/code-reviewer.md`)
- Чек-лист: краевые случаи, состояние гонки, обратная совместимость, безопасность, обработка ошибок, производительность
- Если возможно: кросс-модельное ревью (другая модель проверяет работу Клода)
- **Предупреждение:** у ИИ, проверяющего ИИ, есть общие слепые зоны. Для критичного кода ревью человеком обязательно.

## Гейты

Фаза НЕ может быть отмечена `completed`, пока не пройдены ВСЕ обязательные гейты.

### Уровень 1: обязательные (блокируют фазу)
```bash
# Frontend
cd frontend && npx tsc --noEmit          # 0 ошибок типов
cd frontend && npm run lint               # 0 ошибок линтера
cd frontend && npm test                   # все тесты зелёные

# Backend
cd backend && python -m py_compile app/main.py
cd backend && pytest --tb=short -q
cd backend && ruff check .
```

### Уровень 2: рекомендуемые (для M и L)
```bash
npx madge --circular src/         # циклические зависимости
npm audit --audit-level=high      # уязвимости зависимостей
pip-audit
```

### Уровень 3: глубокая безопасность (этап 10)
```bash
semgrep --config=auto .
# или /security-review
```

Если гейт упал — исправь и прогони заново. Никогда не пропускай.

## Хуки

Хуки уже настроены шаблоном на шагах 5-6 онбординга. Эталонный итоговый файл —
`templates/claude-settings.json.example`. Что там важно с точки зрения Bulletproof:

### PreToolUse — блокировка опасных команд
```json
{
  "matcher": "Bash",
  "hooks": [{
    "type": "command",
    "command": "bash -c \"CMD=$(echo $TOOL_INPUT | jq -r '.command // empty'); echo \\\"$CMD\\\" | grep -qE '(git push.*(main|master)|rm -rf /|DROP TABLE)' && echo 'BLOCKED: Используй feature-ветку / безопасную альтернативу.' >&2 && exit 2 || exit 0\""
  }]
}
```

### Stop — хук против самообмана
```json
{
  "hooks": [{
    "type": "prompt",
    "prompt": "Ты — JSON-оценщик. Отвечай ТОЛЬКО сырым JSON, без markdown.\n\nПроверь финальный ответ ассистента. Отклоняй, если он:\n- оправдывает незавершённую работу ('так было и раньше', 'не входит в задачу', 'сделаю потом')\n- перечисляет проблемы, но не исправляет их\n- пропускает упавшие тесты/линтер с отговорками\n- вносит изменения, не связанные с задачей ('код ради кода')\n- заявляет о готовности, не прогнав гейты верификации\n\nОтвет: {\"ok\": false, \"reason\": \"[что не так]. Вернись и доделай.\"}\nили: {\"ok\": true}"
  }]
}
```

**Важно про сосуществование хуков:** в массиве `Stop` живут ДВА хука —
звуковое уведомление (`type: command`) и проверка на самообман (`type: prompt`).
Они выполняются оба, конфликта нет. Не затирай звуковой хук при добавлении второго.

## Git-дисциплина

- Каждая задача = ветка `feature/<задача>`
- Коммит после каждого пройденного гейта (чекпоинт для отката)
- НИКОГДА не пушь в main напрямую (хук блокирует)
- Squash merge по завершении
- **Стейджь файлы поименно, не `git add .`** — параллельные сессии могут менять файлы,
  которые ты не собирался коммитить. Исключение — самый первый коммит онбординга.

## Дополнительные улучшения (опционально)

### PostToolUse: автоформат после каждой записи файла
```json
{
  "matcher": "Write|Edit",
  "hooks": [{
    "type": "command",
    "command": "npx prettier --write \"$FILE_PATH\" 2>/dev/null || true"
  }]
}
```
Клод пишет аккуратно; хук добивает последние 10%, чтобы не падал CI.

### PreToolUse: блокировка захардкоженных секретов
```json
{
  "matcher": "Write|Edit",
  "hooks": [{
    "type": "command",
    "command": "bash -c \"CONTENT=$(echo $TOOL_INPUT | jq -r '.content // empty'); echo \\\"$CONTENT\\\" | grep -qiP '(api.?key|secret|password)\\s*=\\s*[\\x27\\\"][^\\x27\\\"]{10,}' && echo 'BLOCKED: Секрет в коде. Используй переменные окружения.' >&2 && exit 2 || exit 0\""
  }]
}
```
Хрупко (regex), но ловит очевидные ошибки. Для прода — `semgrep` или `/security-review`.
