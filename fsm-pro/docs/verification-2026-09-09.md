## Этап 6. Верификация — найденные баги

Правило этапа 6: баг считается багом, только если он воспроизводится. Ниже — четыре
находки, каждая с доказательством.

### Баг 1. `POST /api/tasks` падал с 500 — БЛОКИРУЮЩИЙ

**Как воспроизвести:** `curl -X POST /api/tasks -d '{"title":"T"}'`
**Что происходит:** HTTP 500, в ответе HTML со stack trace.
**Причина:** в `INSERT INTO tasks` не передавался `status`, а колонка объявлена `NOT NULL`.
Статус вычислялся отдельной переменной, но в сам запрос не попадал.
**Доказательство:** `SqliteError: NOT NULL constraint failed: tasks.status` (`src/index.js:136`).
**Статус:** ✅ исправлено — `status` добавлен в запрос,初始值 выводится из наличия исполнителя.

### Баг 2. `/admin` и `/worker` отдавали 404 — БЛОКИРУЮЩИЙ

**Как воспроизвести:** `curl -o /dev/null -w '%{http_code}' /admin` → `404`.
**Причина:** `express.static` по умолчанию не подставляет расширение `.html`,
поэтому запрос `/admin` не находил файл `admin.html`.
**Доказательство:** до правки — 404; после `extensions: ['html']` — 200.
**Статус:** ✅ исправлено.

> Оба блокирующих бага были бы найдены и без тестов — но только если бы я догадался
> проверить. Я не догадался: POST не проверял curl-ом, страницы не открывал.
> Их нашли тесты и ручная проверка уже после написания кода. Вывод в ретро.

### Баг 3. Недописанный комментарий стирался каждые 5 секунд

**Как воспроизвести:** открыть карточку задачи в админке, начать печатать комментарий,
подождать 5 секунд.
**Причина:** polling вызывал `renderDetail()`, который пересобирает весь HTML карточки
вместе с полем ввода.
**Доказательство:** `renderDetail()` присваивает `innerHTML` без сохранения значения `input`.
**Статус:** ✅ исправлено — карточка не перерисовывается, пока курсор в поле комментария.

### Баг 4. Взятие задачи было неатомарным — риск несогласованности

**Как воспроизвести:** на странице мастера взятие свободной задачи делало **два** запроса:
`PATCH /status` (new→assigned) и `PATCH /assign`. Если второй не проходил, задача
оставалась в статусе «Назначена» **без исполнителя**.
**Причина:** два независимых запроса вместо одной транзакции.
**Статус:** ✅ исправлено — `PATCH /status` принимает `assigneeId` и меняет всё
в одной транзакции. Добавлен тест на атомарность (23-й).

**Не баг, но зафиксировано:** polling раз в 5 секунд вместо websockets — осознанное
решение итерации. Влияние: при 100+ одновременных пользователях станет проблемой.

## Этап 8. Интеграционная проверка

Прогон сквозного сценария «заявка → назначение → работа → проверка → приёмка»:

| Шаг | Запрос | Результат |
|---|---|---|
| 1. Создать заявку | `POST /api/tasks` | 201, статус `new` |
| 2. Назначить | `PATCH /status {assigned, assigneeId}` | 200, `assigned_to` проставлен |
| 3. Взять в работу | `PATCH /status {in_progress}` | 200 |
| 4. Отправить на проверку | `PATCH /status {under_review}` | 200 |
| 5. Вернуть на доработку | `PATCH /status {in_progress}` | 200 — **не новый статус, возврат** |
| 6. Снова на проверку | `PATCH /status {under_review}` | 200 |
| 7. Принять | `PATCH /status {completed}` | 200 |
| 8. Попытаться вернуть | `PATCH /status {in_progress}` | **400** — конечный статус |
| 9. История | `GET /api/status-history/:id` | 8 записей, с именами и комментариями |

Весь поток проходит. Инварианты PRODUCT-CORE.md соблюдены.

**Честно о том, что НЕ защищено (это уровень демо, а не продукта):**

| Дыра | Серьёзность | Комментарий |
|---|---|---|
| Нет авторизации на мутирующих запросах | **высокая** | любой может сменить статус, зная id задачи |

| CORS открыт на `*` | средняя | любой сайт может дергать API |
| Нет rate limiting | низкая | для демо приемлемо |
| Логин по 4-значному коду без попыток/блокировки | средняя | перебор — 10 000 вариантов |

Всё это осознанные долги итерации и зафиксированы в плане. **Нельзя выдавать за готовый продукт.**
