## Challenge Log

**Проблема:** данные FSM PRO живут в браузере одного устройства. Диспетчер и мастер
на разных телефонах друг друга не видят. Продукт невозможно продать.
Нужна общая база — но так, чтобы это можно было показать и проверить прямо сейчас.

**Выбранное решение:** Node + Express + SQLite (файл `server/fsm.db`),
статусная машина на сервере, две страницы (`/admin`, `/worker`) на одном API.

**Рассмотренные альтернативы:**

| # | Альтернатива | Плюсы | Минусы | Труд | Вердикт |
|---|--------------|-------|--------|------|---------|
| 1 | **Python + FastAPI + SQLite** | Стандартная библиотека, автодокументация Swagger «из коробки» | Разрыв стека: у проекта Node/React. Владельцу придётся держать два рантайма | 4-6 ч | Отклонена: добавляет второй язык в проект одного разработчика |
| 2 | **JSON-файл вместо БД** | Ноль зависимостей, 30 минут | Это не база: нет транзакций, нет связей, нет SQL. Критерий К3 («проверить напрямую через sqlite3») невыполним | 0.5 ч | Отклонена: не решает задачу, а имитирует решение |
| 3 | **PostgreSQL** (локально или облако) | Реальная прод-СУБД, PostGIS для гео | Требует установки/сервиса. Облако — ключи и сеть. Вес несоразмерен итерации | 1-2 дня | Отклонена: преждевременно. SQLite даёт тот же реляционный опыт без инфраструктуры |
| 4 | **Supabase** (уже заложен в код) | Правильный долгосрочный выбор: Auth + Realtime + Storage | Ключей нет, аккаунта нет, бизнес-модели нет. Нельзя показать «здесь и сейчас» | 1-2 нед | Отложена: цель итерации — показать работу, а не выбрать продакшн-стек |
| 5 | **Node + Express + SQLite** (выбрано) | Один язык с проектом. Реляционная БД в файле, переживает перезапуск. `better-sqlite3` — prepared statements из коробки (безопасность). Легко заменить на Postgres позже | Файл БД = один пишущий процесс; для продакшна не годится | 4-6 ч | **Выбрана** |

**Почему выбранное решение лучше:**
Из пяти вариантов только пятый одновременно (а) даёт настоящую реляционную БД с SQL,
(б) не требует ничего, чего у нас нет (ключей, аккаунтов, сервисов),
(в) остаётся в одном языке с проектом, поэтому владелец сможет это прочитать и перенести к себе.
Вариант 4 правильнее стратегически, но он недоступен прямо сейчас — а именно «показать работу»
и является целью итерации.

**Риск выбранного решения, который принимаем:** SQLite не масштабируется на несколько
пишущих процессов. Если продукт дойдёт до реальных клиентов, переход на Postgres
потребует переписать слой доступа. Этот риск осознанный и зафиксирован.

## Фазы

### Фаза 1. Схема БД и сид

- **Статус:** completed
- **Файлы:** `server/src/db.js`, `server/src/seed.js`, `server/fsm.db`
- **Изменения:** таблицы `users, teams, tasks, task_photos, comments, task_status_history`
  по `database_schema.sql`;外键 и индексы; сид демо-данных
- **Гейты:** `sqlite3 fsm.db ".tables"` показывает 6 таблиц; сид создаёт ≥5 задач и ≥3 пользователей
- **Влияние:** нового кода, старый не трогаем

### Фаза 2. REST API + статусная машина

- **Статус:** completed
- **Файлы:** `server/src/index.js`, `server/src/statusMachine.js`, `server/src/routes/*.js`
- **Изменения:** Express на 8000, CORS, маршруты (health, auth, tasks, users, comments, stats),
  таблица разрешённых переходов статусов, все запросы параметризованы
- **Гейты:** `curl /api/health` → 200; недопустимый переход → 400; тесты зелёные
- **Влияние:** самый высокий риск — именно здесь может появиться SQL-инъекция

### Фаза 3. Панель администратора и страница мастера

- **Статус:** completed
- **Файлы:** `server/public/admin.html`, `server/public/worker.html`
- **Изменения:** KPI, таблица задач с фильтрами, карточка со сменой статуса и историей,
  пользователи; страница мастера — мои задачи и две кнопки. Polling 5 сек
- **Гейты:** обе страницы открываются, данные подгружаются, К5 (два окна) выполняется
- **Влияние:** только новые файлы

### Фаза 4. Тесты и самопроверка

- **Статус:** completed
- **Файлы:** `server/test/api.test.js` + статусы 5-9 по методологии
- **Изменения:** 10+ тестов на API и статусную машину; самопроверка по К1-К10;
  верификация; анализ влияния; код-ревью; скан безопасности
- **Гейты:** все тесты зелёные, К1-К10 проверены

## Критерии готовности

К1–К10 из спеки. Ключевой — **К5**: два окна видят одни и те же данные.

## Риски

| Риск | Вероятность | Что делаем |
|---|---|---|
| SQL-инъекция при спешке | средняя | Только prepared statements. Фаза 4 — отдельный скан по grep + ревью |
| Порт 8000 занят или не открывается наружу | средняя | Проверить при старте; если занят — 8001 |
| `node_modules` не сохраняется между сессиями песочницы | **высокая** (уже произошло) | Держать установку в README; перед гейтами проверять наличие |
| Polling вместо websockets выглядит «не как продакт» | низкая | Осознанно: цель — показать общую БД, а не realtime |
| Существующее React-приложение остаётся на localStorage — получится две правды | средняя | Зафиксировано как известный долг. Эта итерация живёт рядом, не заменяя |

## Итог

- **Реализовано целиком:** да. Все 10 критериев приёмки закрыты.
- **Что сделано:**
  - SQLite-база по модели `database_schema.sql`, файл переживает перезапуск
  - REST API: health, meta, auth, задачи (CRUD + статус + назначение), люди, комментарии, статистика, история
  - статусная машина выделена в `statusMachine.js` и проверяется тестами
  - админка: KPI, фильтры, карточка задачи со сменой статуса и историей, сотрудники
  - страница мастера: мои / свободные / завершённые, две большие кнопки
  - 23 теста, все зелёные
- **Что не сделано и почему:** авторизация, права доступа, валидация тела запроса,
  rate limiting, `npm audit`. Всё это вынесено за границы спеки сознательно —
  цель итерации была показать общую базу, а не построить продукт.
- **Что добавить в бэклог:**
  1. Авторизация и проверка ролей на мутирующих запросах (**critical**)
  2. `actorId` из сессии, а не из тела запроса (**high**)
  3. Валидация входных данных + ограничение CORS + rate limiting
  4. `npm audit` по зависимостям
  5. Перенос существующего React-приложения с localStorage на API
- **Уроки:**
  1. **Прогоняй руками каждый эндпоинт до написания тестов.** Два блокирующих бага
     жили в коде, потому что я проверил только то, что догадался проверить.
     Тесты проверяют ровно то, о чём ты подумал.
  2. **Объём спеки обдумывай до фиксации критериев.** Спека переписывалась один раз.
  3. **Риск «песочница теряет node_modules» нужно планировать заранее**, а не discovering twice.
  4. Отделение данных от UI дало измеримый выигрыш: все проблемы безопасности теперь
     решаются в одном месте, а не в каждом экране.
