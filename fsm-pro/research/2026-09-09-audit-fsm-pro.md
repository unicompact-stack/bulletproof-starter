## Что сломано (по убыванию важности)

### 1. Нет бэкенда → это не продукт, а прототип

Все данные живут в браузере одного устройства. **Диспетчер и мастер на разных телефонах не видят друг друга.** Единственный «канал связи» — чат, и то только через `BroadcastChannel` в одном браузере.

Клиент не может этим пользоваться. Никак. Это демо для показа инвестору, не рабочий инструмент.

### 2. Авторизация на 4-значных кодах в localStorage

```ts
// src/auth.ts
const CODES_KEY = 'fsm_access_codes';
export function getAccessCodes(): AccessCodes {
  const raw = localStorage.getItem(CODES_KEY);  // ← коды лежат открытым текстом
```

Любой открывает DevTools → видит все коды, включая личные коды мастеров и код руководителя.
Нет сессии, нет ролей на сервере, нет выхода. Для демо допустимо, для продукта — нет.

### 3. Репозиторий замусорен (и это уже стоило багов)

В git закоммичены:

| Мусор | Объём |
|---|---|
| Собранный сайт в корне: `index.html`, `assets/` (10 файлов от **пяти разных сборок**) | ~1.5 МБ |
| `dist/` (тоже сборка) | ~500 КБ |
| Дубли иконок: `icons/`, `assets/`, `app/public/icons/` — одни и те же PNG/SVG трижды | ~300 КБ |
| `archive/mobile-backup-20260820/` — 10 старых компонентов | ~2 КБ кода |
| `fsm_mobile_demo.html` (38 КБ) и `bossyoki-dashboard-preview.html` (12.6 КБ) — мёртвые прототипы | ~50 КБ |
| `check_gh.py`, `deploy_gh.py`, `gh_check.py` — деплой через GitHub API вместо git | ~10 КБ |

**Это не эстетика.** В CHANGELOG прямо записано: старые деплои заливали сборку в корень, затирали исходный `index.html` — и vite собирал старую версию. Отсюда баг «на сайте всё старое». Структура репо уже стоила часов отладки.

### 4. God-объект: AppContext на 1188 строк

Один файл знает: задачи, пользователей, чат, presence, офлайн-очередь, тосты, синхронизацию вкладок, звук, 9 ключей localStorage.

Типичное следствие — баг из CHANGELOG от 20.08: «Сбросить демо» удалял `fsm_role`, а экран управлялся ключом `fsm_role_selected`. Ключи размножаются, рассинхронизируются, один и тот же баг ловится дважды.

### 5. Три источника правды, два из них врут

| Документ | Что внутри | Статус |
|---|---|---|
| `FSM_System_Architecture_and_Specification.md` | React Native + NestJS + PostgreSQL | **Не существует** |
| `CLAUDE.md` (192 строки) | Половина — хроника сессий 20–21.08 | Устарел как инструкция |
| `CHANGELOG.md` (15 КБ) | Та же хроника, подробнее | Дублирует CLAUDE.md |

Агент, открывший этот проект, прочитает CLAUDE.md, поверит в PostgreSQL и начнёт писать код под несуществующий бэкенд.

### 6. Ноль тестов

`npm run lint` (oxlint) есть, `tsc` есть, тестов — ни одного. При 1188-строчном контексте и 20+ сценариях (взять задачу → фото → отправка → возврат на доработку → принятие) это означает: каждая правка проверяется глазами.

### 7. Нет бизнес-модели

`.business/` нет вообще. Из конкурентного анализа: «Цена: 0 ₽ против 8 000 ₽+/мес».
**0 ₽ — это не цена, это отсутствие ответа.** Не зафиксировано:

- кто платит и за что (за бригаду? за задачу? за мастера?)
- сколько стоит привлечение клиента
- есть ли хоть один реальный клиент (или всё по отзывам владельца)
- что произойдёт, когда появится 10 команд — потянет ли Supabase free tier

## Что уже придумали до нас

Решения для малых команд, на которые стоит смотреть:

| Решение | Что взять |
|---|---|
| **Supabase** (уже заложен) | Auth + Postgres + Storage + Realtime в одном. Бесплатный tier до 500 МБ БД и 1 ГБ файлов — для 10 команд хватит |
| **Connecteam** (бесплатно до 10 чел.) | Модель монетизации: бесплатно до N сотрудников, дальше подписка. Работает именно на малых командах |
| **SafetyCulture** | 100 000+ шаблонов чек-листов — их главный moat. У FSM PRO 3 шаблона. Библиотека шаблонов = самый дешёвый способ создать то, что тяжело скопировать |
| **Jobber / Housecall Pro** | Mobile-first: мастер не должен видеть админку. У FSM PRO это уже есть |

**Вывод по рынку:** ниша «просто, по-русски, дёшево, команда до 15 человек» действительно пустая — это подтверждается. Позиционирование в вашем же документе сформулировано верно.

## Вывод и рекомендация

**Рекомендованный подход: не переписывать с нуля. Выжать продуктовое ядро и пересобрать фундамент.**

**Ключевые причины:**

1. **Проблема не в коде.** Код собирается, выглядит как продукт и содержит 6 сильных UX-находок. Проблема в том, что под ним нет сервера и нет бизнес-модели. Переписать фронтенд с нуля = выбросить 122 коммита и прийти ровно туда же, где вы сейчас, только без находок.

2. **Главная ценность — в документах и решениях, а не в компонентах.** Конкурентный анализ, схема БД, дизайн-система, 5 статусов, «ноль текста» — это то, что копировать тяжело. Реакт-компоненты — как раз то, что переписать легче всего.

3. **Порядок имеет значение.** Сначала бизнес-модель (кто платит), затем сервер (общая база), затем чистка репозитория. Если начать с переписывания UI — получится красивая картинка, которая по-прежнему не работает на двух телефонах.

**Риски этого подхода:**

- Придётся смириться с тем, что первые 2-3 недели видимого прогресса не будет (менять фундамент — значит трогать всё).
- Старый код будет тянуть к себе: «здесь почти работает, давай оставим». Придётся жёстко резать.
- Supabase — это vendor lock-in. Если продукт выстрелит, миграция на свой бэкенд будет стоить денег.

## Три варианта, из которых выбираем

| | Вариант А: Латать | Вариант Б: Выжать и пересобрать | Вариант В: С нуля |
|---|---|---|---|
| **Что делаем** | Подключить Supabase к существующему контексту, почистить репо | Вынести продуктовое ядро в документы, переписать слой данных и авторизацию, UI переиспользовать | Новый репозиторий, новая архитектура, переносим только идеи |
| **Срок** | 1-2 недели | 3-5 недель | 2-3 месяца |
| **Результат** | Работает на двух телефонах, но god-контекст остаётся | Работает, расширяемо, есть тесты | Идеально, но поздно |
| **Риск** | Через месяц упрётесь в тот же контекст | Нужна дисциплина, чтобы не скатиться в «латание» | Выгорание; конкурентное окно закроется |
| **Кому** | Если нужен быстрый показ клиенту | Если продукт всерьёз | Если есть деньги и время |

**Рекомендация — Вариант Б.** Он единственный, где вы и сохраняете то, что уже наработано,
и устраняете настоящую причину проблем (нет сервера, нет бизнес-модели).
