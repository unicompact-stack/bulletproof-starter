# Спека: Сервер и панель администратора FSM PRO v0.3

**Дата:** 2026-09-09
**Автор:** владелец (решение: «работаем в песочнице, сделай свою базу и админку, пройди все фазы»)
**Связь с бизнесом:** без общей базы продукт не может быть продан ни одному клиенту —
это первая итерация, которая устраняет именно это препятствие.

---

## Проблема

1. Данные FSM PRO живут в браузере одного устройства. Диспетчер и мастер на разных
   телефонах друг друга не видят. **Это делает продукт непродаваемым.**
2. Нет способа посмотреть на данные со стороны: что в базе, сколько задач,
   кто что делает. Всё только через UI приложения.
3. Правила переходов статусов размазаны по React-компонентам. Логика, которая
   должна быть общей для всех клиентов, живёт в интерфейсе одного из них.

---

## Цель

Поднять в песочнице **настоящий сервер с реляционной базой** и **панель администратора**,
работающую с этой базой через REST API. После этого данные перестают быть свойством
конкретного браузера, а правила статусов становятся общими для всех клиентов.

**Измеримый результат:** два разных окна браузера видят одни и те же задачи;
изменение статуса в одном окне появляется в другом; база лежит в файле и переживает
перезапуск сервера.

---

## Область

### Входит

1. **Схема БД (SQLite)** по модели `database_schema.sql`:
   `users`, `teams`, `tasks`, `task_photos`, `comments`, `task_status_history`.
2. **Сервер** (Node + Express): REST API, порт 8000, доступен извне (`0.0.0.0`).
3. **Статусная машина на сервере** — таблица разрешённых переходов.
   Недопустимый переход отклоняется с понятной ошибкой, а не молча применяется.
4. **API**: health, auth/login по коду, задачи (список/создание/детально/смена статуса),
   пользователи, комментарии, статистика, история статусов.
5. **Сид данных** — перенос текущих демо-задач и пользователей в базу, чтобы было что показать.
6. **Панель администратора** — отдельная страница на `/admin`:
   KPI-карточки, таблица задач с фильтром по статусу, карточка задачи со сменой статуса
   и историей, список пользователей. Обновляется сама (polling).
7. **Страница мастера `/worker`** — мобильный вид: мои задачи, «взять в работу»,
   «отправить на проверку». Работает с той же базой, что и админка.
   Две страницы одного сервера = наглядная демонстрация общей базы.

### Не входит

- Реальная авторизация (JWT, сессии, хеширование паролей). Коды остаются демо-уровня.
- Загрузка фото на сервер (фото остаются локальными в браузере).
- Push-уведомления и websockets (вместо них — polling).
- Миграции, бэкапы, RLS, multi-tenancy.
- Деплой куда-либо кроме песочницы.
- Перенос существующих экранов React-приложения — вместо этого создаётся
  новое приложение, работающее с API.

> Причина: цель итерации — показать работающую общую базу и пройти полный цикл методики,
> а не дописать продакт. Всё перечисленное остаётся долгом и фиксируется.

## Критерии приёмки

- [ ] **К1.** Файл базы `server/fsm.db` существует, переживает перезапуск сервера.
- [ ] **К2.** `GET /api/health` возвращает `{"status":"ok","db":"up","tasks":N}`.
- [ ] **К3.** `GET /api/tasks` отдаёт задачи из базы, а не из памяти процесса.
      Проверка: изменить запись напрямую через `sqlite3` → API отдаёт новое значение.
- [ ] **К4.** Недопустимый переход статуса (`new` → `completed`) отклоняется
      с HTTP 400 и понятным сообщением. Допустимый — применяется и пишется в историю.
- [ ] **К5.** Два разных окна браузера видят одни и те же задачи; смена статуса
      в одном окне появляется в другом не более чем через 5 секунд.
- [ ] **К6.** Панель администратора на `/admin` показывает: 4 KPI, таблицу задач
      с фильтром по статусу, карточку задачи со сменой статуса и историей, список пользователей.
- [ ] **К7.** Страница `/worker` показывает задачи мастера из базы; действие на ней
      («взял в работу», «отправил на проверку») видно в админке.
- [ ] **К8.** Каждый SQL-запрос параметризован. Проверка: `grep` по `server/src` не находит
      конкатенации пользовательского ввода в SQL-строке.
- [ ] **К9.** Тесты API: минимум 10 кейсов, все зелёные (схема, CRUD, переходы статусов, валидация).
- [ ] **К10.** Гейты: сервер стартует, `curl /api/health` → 200, тесты зелёные,
      админка открывается и показывает данные.

> **К5 — ключевой.** Это тот критерий, который отличает «настоящая база»
> от «очередная имитация». Всё остальное проверяется ради него.

## Ограничения

- **Только песочница.** Ничего не уходит на GitHub и не деплоится.
- **Без внешних сервисов.** SQLite-файл, никаких облачных БД и ключей.
- **Один порт наружу** (8000) для сервера и админки; React-приложение — на 5173.
- **Браузер не должен обращаться к `localhost`** — админка использует относительные пути,
  приложение — тот же origin, что и API (проксируется dev-сервером).
- **Монетизация по-прежнему не определена** — схема БД содержит `companies`,
  но бизнес-логики тарифов и лимитов нет.
