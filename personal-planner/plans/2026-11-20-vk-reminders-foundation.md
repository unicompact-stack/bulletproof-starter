# Безопасная подготовка к напоминаниям ВКонтакте

## План до разработки

1. Не включать напоминания и не передавать фактические задачи; не менять календарь или пользователя.
2. Реализовать отдельный переносимый модуль отправки в VK с выключенной по умолчанию настоящей отправкой; ключ и ID получателя брать только из окружения, не сохранять в репозиторий или логи.
3. Модуль должен возвращать безопасный результат при транспортных и API ошибках, ограничивать время ожидания и использовать стабильный идентификатор сообщения для безопасных повторов. Никаких зависимостей и внешних сетевых запросов в тестах.
4. Учитывать локальное хранение календаря, требования к защите будущего сервера, хранению/синхронизации, планировщику и неудобства тарифов. Не выдавать эту основу за готовый деплой или синхронизацию.
5. Проверки: 1) без токена; 2) без явного включения; 3) валидация получателя; 4) проверка сообщения; 5) успешный ответ имитации; 6) ошибка ВК; 7) таймаут/ошибка сети; 8) повтор с прежним random_id; 9) нет секретов/личного текста в логах; 10) существующие тесты календаря без изменений.
6. Открытые решения до автоматических напоминаний: поставщик сервера, защита и хранение личных задач, частота/точность, выбор напоминаний, правила устаревших/повторных событий и ясное согласие на отправку. Никаких подтверждений об успешной работе с реальным VK без настоящей проверки.

## Итог

- Реализован выключенный по умолчанию адаптер и 9 изолированных тестов; существует отдельный явный тест отправки после самостоятельной настройки, но настоящий VK не проверялся. Нет автоматической синхронизации, базы, расписания и деплоя.
- Старые сценарии: 26/26 логика и 23/23 Chromium; реальный календарь пользователя не затрагивался.
- Сравнение хостингов и отсутствующих компонентов в `vk-reminders/README.md`; без выбора поставщика и согласования хранения нельзя объявлять готовность для личных данных.
