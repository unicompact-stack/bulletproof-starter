# Подготовка к напоминаниям ВКонтакте

## Что готово и чего нет

Здесь находится **только серверный адаптер отправки и его тесты**. Это не готовый сервер и не подключение к календарю. Адаптер не читает календарь, не синхронизирует задачи, не создаёт хранилище или расписание и не запускается автоматически. Интерфейс планировщика не менялся. Токенов и настоящих ID в проекте нет.

Напоминания **выключены**. По умолчанию выполняется проверка без сети, не требующая ключа. Изолированная тестовая команда может отправить одно заранее заданное сообщение, но только при явном подтверждении и после самостоятельной настройки секретов. Эта отправка ещё не проверена с настоящим VK.

## Проверка без ВКонтакте

Требуется Python 3.10 или новее, дополнительных библиотек не нужно. Из корня репозитория:

```bash
python3 -m unittest discover -s personal-planner/vk-reminders -p 'test_*.py' -v
python3 personal-planner/vk-reminders/vk_sender.py
```

Оба действия не обращаются к VK. В модульных тестах ответы сервера имитируются.

## Позднее: только вручную проверить связь с VK

До проверки необходимо подтвердить в актуальной документации VK используемую версию API, тип ключа и права на сообщения. У сообщества должны быть включены сообщения; получатель должен иметь право получать сообщения от сообщества (например, согласиться или написать первым — точные условия проверить в VK). Создайте отдельный ключ сообщества для этого проекта, если такая возможность доступна.

В **защищённом окружении сервера** задайте две переменные (не в коде, истории команд, репозитории, чатах, клиентском JS или логах):

- `VK_TOKEN_MESSAGES` — секретный ключ сообщества с необходимыми правами;
- `VK_USER_ID` — числовой ID получателя личного сообщения.

ID сообщества соответствует ключу и **не используется этим адаптером**. Он не проверяет принадлежность токена сообществу, поэтому это нужно проверить самостоятельно. Не используйте в проекте примерные ID из других переписок без подтверждения владельца и получателя.

После настройки секретов, только если желаете получить **одно** реальное тестовое сообщение:

```bash
python3 personal-planner/vk-reminders/vk_sender.py --send-test --confirm
```

Команда отправляет только фиксированный тестовый текст, не личные задачи. Реальное сообщение, стоимость/доступность платформы и работа API не проверены в этой среде. Настоящая отправка требует внешнего доступа к `api.vk.com` и разрешения VK. Проверяйте права и настройки сообществ, если получен код ошибки VK.

После ответа с сетевой ошибкой неизвестно, дошло ли сообщение. Команда выводит ID попытки; если нужно повторить **то же** сообщение, используйте `--random-id <ID попытки>` вместе с `--send-test --confirm`. Модуль сам не выполняет повторов. Нет гарантии доставки ровно один раз: поведение дедупликации зависит от VK. При ошибке настройки попытка не отправляется. Не вставляйте секреты в аргументы командной строки и не публикуйте снимки настроек окружения.

## Архитектура для следующего этапа

Для работы с календарём понадобятся: личное долговременное хранилище, аутентификация пользователя, защищённое подключение HTTPS, явный выбор задач/напоминаний, безопасная передача состояния, хранение расписания и факта отправки, управление повторами и изменениями задач, резервное копирование и процесс/планировщик. Все эти части ещё предстоит спроектировать и реализовать. Перенос календаря с одного адреса на другой не переносит browser localStorage автоматически; нужен экспорт/восстановление или безопасная синхронизация с контролем конфликтов. Не храните сессии в публичном репозитории и не размещайте личные данные в общедоступном preview.

Нельзя давать браузеру ключ VK или открытый публичный endpoint, который отправляет сообщения. По умолчанию сообщения не должны включаться на все задачи: согласие и настройки выбирает пользователь. Планировщик должен учитывать часовой пояс, задержки/отключения, отменённые и изменённые задачи, предотвращать дубли, а уведомления не гарантируют доставку вовремя. Безопасность и восстановление проверить до переноса реальных данных.

## Размещение: предварительно, не развёрнуто

- **Свой компьютер/домашний сервер** — низкие расходы при наличии устройства, но напоминания работают только во включённом и подключённом к интернету состоянии. Для доступа с телефона извне нужно отдельно продумать безопасный доступ.
- **Постоянно работающий виртуальный сервер** — гибко: приложение, хранилище и фоновая проверка могут работать вместе. Нужны настройка, обновления, резервные копии и расходы на сервер; стоимость и доступность из РФ проверять у конкретного поставщика.
- **Render** — возможен после доработки приложения и настройки защищённой базы. Бесплатное приложение засыпает, а локальные файлы теряются при перезапуске; бесплатная база ограничена по сроку. Cron не имеет доступа к постоянному диску; периодические задачи и постоянное хранилище могут быть платными. См. https://render.com/docs/free и https://render.com/docs/cronjobs .
- **Vercel Hobby** — ограничения различаются для Cron Jobs и новых Schedules. По документации Cron Jobs — не чаще раза в сутки и с возможной задержкой до часа; Schedules — не чаще 15 минут и с 15-минутным окном запуска. Для точного напоминания за 15 минут этого недостаточно. См. https://vercel.com/docs/cron-jobs/usage-and-pricing и https://vercel.com/docs/schedules/limits . В любом случае нужна отдельная защищённая постоянная база.
- **GitHub Actions** — возможны задержки или пропуски; расписание работает на основной ветке, может отключаться по неактивности. Не подходит для гарантированных напоминаний. См. https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows .

Условия и тарифы меняются: проверять до регистрации/оплаты. Ничего не покупается и не подключается автоматически.
