# Передача проекта: календарь, Supabase, Render и напоминания ВК

Этот файл предназначен для человека и помощника по программированию, который продолжит работу в другой среде. Он содержит договорённости и техническое состояние, но **не является резервной копией задач и не содержит полной истории чата**. Никаких паролей, токенов, реальных ID или личных задач здесь нет.

## Короткое поручение для нового помощника

> Прочитай `personal-planner/ПЕРЕДАЧА-RENDER-SUPABASE-ВК.md`, `STATE.md`, `README.md`, а также `render/README.md` и `vk-reminders/README.md`. Продолжи подготовку существующего персонального планировщика к защищённому хранению через Supabase и необязательным напоминаниям ВК с серверной частью на Render. Сначала проверь код, действующие условия сервисов и составь понятный план с проверками. Реализуй по шагам, не теряя старые задачи и не включая отправку молча. Разъясняй новичку простым языком, без лишних вопросов. Не считай систему уже подключённой и не запрашивай секреты в чате. Не создавай платные ресурсы, не меняй чужие или существующие сервисы и не отправляй настоящие сообщения без отдельного подтверждения пользователя.

## Принятые решения и цель

- Это лёгкий личный календарь и планировщик, а не только система напоминаний. Важны списки дел **без даты**, заметки и необязательные маленькие шаги. Не заставлять пользователя назначать время каждой задаче; не перегружать план.
- Пользователь выбрал **Render** как место для будущей серверной части и подтвердил наличие проекта **Supabase** для базы. Он также использует сообщество ВК и упоминал другое приложение BossYoki. Не предполагаем, что оно постоянно работает, доступно новому помощнику или что его можно менять.
- Желаемый пример: пользователь явно включает напоминание для задачи, указывает дату и время; задача надёжно сохраняется и синхронизируется; сервер на Render проверяет расписание; сообщение от сообщества ВК приходит пользователю. «За 15 минут» — лишь пример, не универсальное обязательное правило. Дела без даты/времени не должны по умолчанию получать случайное время или рассылаться.
- Токен сообщества пользователь **пока не передавал** и передавать в чат не должен. Никакие реальные ID из стороннего примера не считать подтверждёнными автоматически. Отправка — по личному согласию и после теста; все новые напоминания по умолчанию выключены.
- Пользователь намерен перенести репозиторий в другую среду и запустить там помощника. Выбор сервиса уже сделан, но схема входа, тариф/бюджет, проект/база, форматы уведомлений, правила синхронизации и доступность реальных аккаунтов **ещё не согласованы и не проверены**.

## Что сейчас реализовано

1. `app/` — браузерный календарь на JavaScript: неделя/месяц/год; задачи и история; списки без даты; заметки, предложения, статусы, частичный прогресс и шаги с галочками. Изменения сохраняются локально в `localStorage` для конкретного адреса и браузера. Шаги не завершают родительскую задачу автоматически.
2. «Сохранить сессию» создаёт JSON с состоянием и отчётом, для резервирования и восстановления; есть системный диалог при поддержке браузера и альтернативы. Истории чата в JSON нет. Поддерживаются старые копии, UTF-8, UTF-16 с BOM и предполагаемая Windows-1251 с подтверждением. Операция восстановления заменяет текущее состояние после подтверждения.
3. `render/` — тестовая сборка и Blueprint **только для публичного статического сайта**, копирующие ограниченный набор разрешённых демофайлов. Это не защищённое облачное хранилище и не сервер напоминаний. README объясняет конфигурацию, угрозы и проверку 404 временного канала.
4. `vk-reminders/vk_sender.py` — отдельный адаптер к VK API и безопасная проверка без реальной сети. Настоящая отправка по умолчанию выключена; тестовая отправка возможна только при явном запуске и настройке секретов. Функция не читает календарь, не планирует и не повторяет отправки. Версия VK API и разрешения нуждаются в проверке по актуальной документации.
5. Последняя проверка: 29 модульных JS-тестов, 9 тестов адаптера ВК с имитацией ответов, 23 браузерных сценария на собранном сайте, отдельная проверка публичной сборки и мобильной ширины. Это не доказывает работу на устройстве пользователя или в реальном Render/VK.

## Чего ещё нет — важно

- Нет подключённой базы Supabase, системы входа и разграничения доступа, серверного API или синхронизации между устройствами.
- Нет автоматического расписания, напоминаний по задачам, устойчивой очереди и журнала отправки.
- Нет развёртывания этого проекта на Render, нет проверенной конфигурации текущих сервисов пользователя и нет настоящего теста отправки через ВК. Статический Blueprint не выполняет Python и не должен получать VK-токен.
- Репозиторий проекта публичный. Игнорируемый `app/local-inbox/latest.json` доступен по URL обычного предпросмотра и **не является защищённым каналом**. `.gitignore` не шифрует данные. Личные сессии и токены не публиковать. Файлы в игнорируемых директориях при скачивании репозитория могут отсутствовать; не рассчитывать на них.
- Ассистент не видит автоматически задачи в браузере пользователя, его кабинеты или текущие условия аккаунтов. Не обещать сохранность, доступ к истории чата или доставку сообщения ровно в минуту.

## Ожидаемая работа следующего помощника

### 1. Безопасность и архитектура

- Перед кодом описать в чате план и не менее 10 конкретных проверок. Уточнить только решения, без которых нельзя продолжать; не запрашивать и не принимать пароли, ключи, коды подтверждения в чате.
- Сверить текущую документацию Supabase, Render и VK. Предложить минимальную конфигурацию и расходы **до создания ресурсов**: в частности, учесть засыпание бесплатных серверов Render, срок и ограничения тарифов баз, надёжность расписания и резервное копирование. Не предполагать, что cron Render видит диск другого сервиса.
- Спроектировать защиту: личная аутентификация, проверка прав на уровне сервера и/или Supabase RLS для каждой записи, разграничение пользователей, HTTPS, защита от неавторизованных запросов, безопасная работа сессии и секретов. Проверить отрицательные сценарии и отсутствие личных данных в публичном сайте, логах и Git. Не оставлять публичный endpoint, позволяющий посылать сообщения.
- Секреты Supabase с повышенными правами и VK-токен — только на доверенной серверной стороне или в защищённых настройках провайдера; не отправлять в браузер, репозиторий, сообщения, логи или URL. Если используются публичные ключи клиента Supabase, они **не заменяют RLS**; конфигурацию прав тестировать отдельно. Оператор сервиса/провайдера может иметь доступ к данным: не обещать сквозное шифрование, если оно не реализовано.

### 2. Данные и перенос без потери

- Перед миграцией показать пользователю, как сохранить и проверить резервную JSON-сессию; не удалять и не перезаписывать локальные данные без явного подтверждения. На новом адресе Render будет другое localStorage.
- Спроектировать безопасный импорт и синхронизацию: выбор источника, предварительный просмотр, повторный импорт без дублей, обработка ошибок, конфликтов, офлайна, нескольких устройств и случайной устаревшей копии. Нельзя молча заменять существующую базу пустым состоянием. Сообщать о несохранённых изменениях.
- Сохранить существующие поля и поведение, в том числе задачи без даты, статусы, историю, заметки, предложения, счётчики и необязательные шаги. Поддерживать старые JSON-копии. Сверить реализацию в `app/logic.js` и формат `session()`, а не предполагать структуру.
- Не записывать личные данные в открытый Git/предпросмотр. Проверять сначала на вымышленных данных, затем реальный перенос — только по явному согласию пользователя.

### 3. Напоминания

- Согласовать UI: отдельное включение уведомления, выбор времени/часового пояса и отключение. По умолчанию выключено, в том числе для уже существующих задач; не вводить время в задачи без него автоматически.
- Серверная проверка только явно включённых и актуальных уведомлений. Учесть изменение даты, времени, текста, статуса, отмену, удаление, остановку сервиса и задержку синхронизации. При ошибке передачи не делать вид, что отмена/изменение уже дошли до сервера.
- Использовать постоянное состояние отправки, безопасную конкурентную обработку и идентификатор `random_id`, постоянный для повторов одного уведомления, а не новый при каждой попытке. Различать успех VK, отказ и неоднозначный сетевой сбой; ограничивать повторы и устаревшие уведомления. Не обещать абсолютную защиту от дублей/потерь без подтверждения поведения платформы.
- Сначала автоматизированные тесты с подменой VK и искусственным временем; затем, после разрешения пользователя и настройки секрета им самим, одно понятное тестовое сообщение. Реальную доступность VK API, права токена и разрешение получателя проверять отдельно. На странице VK и в логах не показывать токен.

### 4. Что показать пользователю

Понятно сообщить: что уже работает и что ещё нет; где находятся данные; сколько может стоить выбранная схема; как включить и выключить уведомления; как сохранить резервную копию, перенести состояние и что произойдёт при сбое. Не выдавать успешную имитацию за реальный отправленный VK-тест. Попросить отдельное подтверждение перед отправкой реальных задач или изменениями в существующих сервисах.

## Базовые проверки из корня репозитория

```bash
node --test personal-planner/app/logic.test.js personal-planner/render/build.test.cjs
python3 -m unittest discover -s personal-planner/vk-reminders -p 'test_*.py'
node personal-planner/render/build.cjs
```

Для браузерных проверок нужны отдельно установленный `puppeteer-core`, Chromium и локальный сервер, пути и команда описаны в тестах и README. Не использовать личный браузерный профиль в тестах. Наличие зависимостей и платформенные ограничения в новой среде надо проверить отдельно.
